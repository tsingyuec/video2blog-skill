# 博客写作规范（金字塔写作风格 + 初学者可读）

本规范用于把 `transcripts/<视频标题>.md`（原始文稿：图片 + 合并字幕 + 时间戳）改写成 `blog/<标题>.md`。

## 0. 第一原则：基于文稿，不凭空发挥

- 内容必须来自原始文稿（字幕 + 幻灯片）；不得编造视频之外的事实。
- 字幕可能由 AI 生成（B 站 AI 字幕 / YouTube 自动字幕），存在生成不准确的情况，要结合上下文纠正，例如：
  - `cs three three nox` → **CS336**
  - `PERCY` → **Percy Liang**；`TO/TAC` → **Tatsu**；`兔20年` → **20 年**
  - `tension`（双关语处）→ **attention（注意力）**；`mob two` → **Mamba-2**
  - 术语、论文名尽量还原正确拼写；拿不准的人名/数字**保持中性表述**（如「来自中国的开源权重模型」），**不要编造**。
- **讲者没说的因果、算法细节、论文结论不写**。补充背景知识时标明「补充（非讲者原话）」，并确保补充内容可核验；不要用补充内容冒充视频观点。
- **幻灯片自身可能有错**：模板残留、图文标反、笔误。以可核验的画面事实为准，不照抄错误标注，也不臆造「讲者其实想说……」。
- **英文视频**：术语首次出现给中文 + 英文原文；引文翻译要忠实，不要为了通顺改变原意；不确定的数字保持原文或做中性表述。
- 文稿是证据，不是成稿。不要整段粘贴窗口文本；必须改写成有结构的文章。

原始文稿的窗口文本是字幕逐句拼接，直接照抄会不通顺。写博客前先**逐窗口改写**：

- 可以润色、合并断句、纠正错拼，但**不得丢信息**；无字幕窗口左栏的「（此区间无字幕）」保持原样。
- 只改表格左栏的字幕文本，不动标题、图片路径、窗口顺序。
- 用 `scripts/pipeline/transcript_windows.py dump`（导出 `NNNNN|文本`）+ `scripts/pipeline/transcript_windows.py apply`（heredoc 写回，**必须写结束分隔符**）做「导出 → 改写 → 写回」循环，每批 30–60 个窗口。
- 改写完成后**不要重跑** `build_transcript.py`（会覆盖已修复文本）。

**写作前梳理**：文稿讨论的内容可以分为很多段，这些内容中有些分段可能没有梳理清楚。读取文稿中对应窗口的代表帧，结合画面理解这段在讲什么；只有梳理清楚，编写博客时才能把对应内容表达清楚。

## 1. 金字塔写作风格（把思想组织成「金字塔」）

**四条原则（写完逐条自检）：**

1. **结论先行**：全文或每节先把中心思想（结论）放在最前面，再展开理由。
2. **以上统下**：上一层是下一层的总结概括。例如「水果」概括「苹果、梨、香蕉」。
3. **归类分组**：同一组里的思想必须属于同一逻辑范畴（可被同一个名词概括）。
4. **逻辑递进**：组内按某种逻辑顺序排列。

**序言用 SCQA（背景-冲突-疑问-回答）：**

- 背景（S）：读者已知的事实。
- 冲突（C）：出现的变化/问题。
- 疑问（Q）：冲突自然引出的疑问。
- 回答（A）：你的中心思想（= 全文结论，做到结论先行）。

只写读者已知的信息作为背景；别把新信息塞进序言。

**MECE：** 组间「相互独立、完全穷尽」。快验：任一项挪到另一组也说得通 = 有重叠；沿流程走一遍发现漏项 = 不穷尽。

**一组要点 3–5 个最佳**（人短期记忆 7±2，最好只放 3 个）。超过就分组、提高抽象层。

**组内只有 4 种逻辑顺序：** 时间/步骤、结构/空间（整体→部分）、程度/重要性（最重要→次重要）、演绎（大前提→小前提→结论）。找不到任何一种 = 这组思想无逻辑关系，回去重新分组。

**归纳优先于演绎：** 关键句层次用「归纳」（并列理由，读者易跟）；只有在需要严格证明的下层才用「演绎」。

**标题要传递观点：** 写完整判断句（如「前置归一化更利于大模型训练」），不要只写分类词（如「归一化对比」）。

## 2. 初学者可读

- 目标读者：初学者。
- **术语首次出现必须当场解释并举例**。
- 每个概念讲清三件事：**是什么 → 为什么需要 → 怎么做 / 举个例子**。
- 多用类比与具体例子；抽象处一定落地。
- 英文术语、缩写、论文名首次出现时给出原文与中文；不要假设读者知道。
- 公式不要只贴结论：说明每个符号是什么、这一步为什么成立、它在整条推导里的位置。
- 代码片段要能读懂：交代输入输出、关键变量、与正文概念的对应关系。

## 3. 文章结构模板

```markdown
# <知识点标题：判断句或名词短语>

## 本讲要解决的核心问题（SCQA）
**背景**：…
**冲突**：…
**疑问**：…
**回答（中心思想）**：…          ← 结论先行

## 一、<章节名（观点句）>
### 1.1 <小节名>
正文…（可含列表、公式、伪代码、配图、时间戳）

### 1.2 <小节名>
…

## 二、<章节名>
…（全篇通常 6–10 章；按内容逻辑分组，不要用「## 要点N：…」的平铺风格）

## 小结
- 3–8 条，金字塔式回顾

## 关键术语速查
| 术语 | 一句话解释 |
| --- | --- |
```

- 单集课程可用 `# 第N讲：<主题>`；知识库小节用知识点标题，并用副题或措辞点出本视频的角度，避免同一小节多篇重名；不要把视频标题直接当文章标题。
- 章节标题写观点，不写「第一部分」「相关概念」这类空分类。
- 一篇只回答一个中心问题；如果发现两个中心问题，按下一节的拆篇规则处理。

### 3.1 拆篇

视频接近或超过 60 分钟时，可以视内容结构考虑拆篇：

- 视频本身有两个相对独立、各自能回答一个中心问题的部分，拆成两篇读起来更清楚；
- 只有一个中心问题，或拆开后每篇都要重复大量背景，就不拆；
- **不要为了拆篇而拆篇**；30–45 分钟信息密度高，也可以是一篇；60 分钟结构清楚，也可以是一篇。

拆篇的写法：

- 文件名加标号：`<标题>-1.md`、`<标题>-2.md`；配图目录同名（`assets/<标题>-1/`）。
- 每篇独立 SCQA、小结与至少 10 个时间戳，文首互相链接。
- 把内容按知识边界切开，不要把同一段在两篇里各写一遍；背景只在新篇首次出现处补一次。

## 4. 配图

### 4.1 数量

- 单篇 8–16 张；拆篇后每篇按自己的内容量取 8–16 张。
- 每张图都要服务一个段落；只为「看起来丰富」而加的图，删掉。

### 4.2 读图规则

- 配图挑选最影响成品：去重留下的代表帧 ≠ 有用帧，图的作用是帮助读者理解博客内容，务必**逐张读图核对**后再入选。
- 用 Read 工具读图，**一次只读 1 张，每轮最多 3 张**，绝不超限（超限会被模型接口直接拒绝）。
- 核对：图是否对应当前段落、是否空白/重复/错位；错位就换图或调顺序，空白就删掉。
- 替换配图后清理不再被引用的孤立图片。

### 4.3 选图

- **优先**：含文字 / 图表 / 公式 / 示意图 / 代码 / 对比表的幻灯片。
- **剔除**：纯产品渲染、Logo、装饰与转场帧、标题帧、动画未展开的灰字帧、讲者头像、PPT 编辑视图。
- 一张图只说明一件事；直接使用代表帧原图，保持原始画面与上下文。

### 4.4 落位与命名

- 从 `transcripts/img/<视频ID>/` 挑图，复制到博客的 `assets/<博客名>/`，沿用秒数命名（`00060.webp` = 第 60 秒）。
- 引用：`![图注](assets/00060.webp)`，路径相对博客文件。
- 图片目录名与文件名不要含半角括号 `()`；必须保留时，链接里写 `%28` / `%29`，空格写 `%20`，不要用 `<...>` 包裹。

### 4.5 图注

- 图注用一句话说明「这张图帮读者理解什么」，不要复述图片标题。
- 图注 alt 文本不要出现 `[` 或 `]`（会截断 alt 导致图片不被引用），用 `\lbrack` / `\rbrack` 或改写措辞。
- 公式图要在图注里点出关键符号，方便读者对照正文。

## 5. 时间戳跳转链接

关键知识点处插入：

```markdown
[【跳转到 MM:SS】](https://www.bilibili.com/video/<BV>/?t=<秒>)
```

- 其中 `t` 为整数秒，`MM:SS` 由 `t` 换算，两者必须一致。
- 时间戳链接统一写成 `...?t=<秒>`。
- YouTube 用 `&t=<秒>`。
- 链接文字统一用 `【跳转到 MM:SS】`，方便读者识别。
- 链在关键结论、推导起点、代码演示、实验对比处；不要每句都链。

### 5.1 数量要求

**每篇至少 10 个时间戳，并随视频时长递增。** 建议按 `max(10, ceil(时长分钟 / 4))` 取：

| 视频时长 | 最少时间戳 |
| --- | --- |
| ≤ 40 分钟 | 10 |
| 60 分钟 | 15 |
| 90 分钟 | 23 |
| 120 分钟 | 30 |

- 分散在各章，每个关键结论/推导/实验/代码演示处一个；不要堆在开头或结尾。
- 重复引用同一时间点只算一个；只写链接、正文没有对应内容的，不算有效时间戳。
- 拆篇后每篇按自己覆盖的片段时长分别计算，且各自不少于 10 个。
- 发布时间戳前，把 `t` 换算成 `MM:SS` 核对一遍，确保显示时间与链接秒数一致。

## 6. 篇幅与覆盖

- **完整覆盖**文稿中的所有讨论内容，不得为省事省略；宁可长，不可粗。
- 篇幅随视频时长与信息量而定；写完统计字数，对照视频时长、文稿窗口数，判断是否过度概括或注水。
- 合理省略的只有：寒暄、课程通知、设备调试、与主题无关的闲聊。难讲的推导、实验细节、边界条件不能省。
- 视频接近 60 分钟时，按 §3.1 判断是否拆篇；拆篇后每篇仍要完整覆盖自己负责的部分，不能把难讲的内容推给另一篇。

## 7. 长文任务的工程建议

- 单次读取过长的文稿，容易因负载过大而中断，可分段进行读取。
- 写入博客时同理，分多次追加写入文件，避免单次写入内容过多而中断。
- 先写骨架（标题、SCQA、章标题），再逐章填内容；每填完一章做一次覆盖核对。

## 8. 排版与路径

| 项目 | 写法 |
| --- | --- |
| 行内公式 | `$V_\pi(s)$` |
| 独立公式 | `$$` 独占一行，前后各留一个空行 |
| 伪代码 / ASCII 图 | 保留围栏代码块，不要硬转 LaTeX |
| 表格内公式 | 用 `\vert` / `\lvert`，不用裸 `|` |
| 图注 alt | 不含 `[` / `]`；用 `\lbrack` / `\rbrack` |
| 图片 | 标准 Markdown，不写 `width` 属性 |
| 标题层级 | `#` 文章标题，`##` 章，`###` 小节，不跳级 |
| 文件名 | 不含半角括号；空格在链接里写 `%20` |

**不要用代码样式写公式**（`` `V_{π_k}` ``）——线上会显示成带下划线和花括号的等宽文本。

**转义**：`\theta` 这类命令若经 Python 字符串写入，`\t` 会变成真实制表符导致公式失效。用原始字符串或双反斜杠，写完 `grep -Pn '\t' <文件>` 确认。

## 9. 交付前自检

- [ ] 标题是知识点，不是「视频笔记」；开头有 SCQA，结论先行
- [ ] 章节按知识逻辑分组，标题写判断句；一组要点 3–5 个
- [ ] 术语首次出现有解释；公式符号有交代；英文术语有原文
- [ ] 逐窗口核对过，没有遗漏难讲的段落
- [ ] 讲者没说的内容没有编；补充知识标了「补充（非讲者原话）」
- [ ] 配图逐张读过；图注说明「帮读者理解什么」；没有标题帧/灰字帧/Logo
- [ ] 配图使用代表帧原图，画面与公式完整
- [ ] 时间戳至少 10 个，随时长递增，分散在各章；`MM:SS` 与 `t` 一致
- [ ] 拆篇时文件名带 `-1` / `-2`，各篇有独立 `assets/` 与互链
- [ ] 公式、表格、路径、转义符合第 8 节
- [ ] 字数与视频时长/文稿信息量匹配；没有过度概括或注水
- [ ] `check_blog`、`check_images`、`check_md_math`、`check_katex` 全部通过
